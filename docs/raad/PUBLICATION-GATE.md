# بوابة اعتماد الخادم — مفعّلة في إنتاج شُرفة

**التحديث الإنتاجي 2026-10-28:** اكتمل التركيب وفصل الاتصال وإعادة النشر والتحقق من استعمال `raad_web` فعليًا. سجل التنفيذ والنسخة الاحتياطية والنتائج والمتبقي للأتمتة في [PRODUCTION-ROLLOUT.md](PRODUCTION-ROLLOUT.md). الخطوات أدناه خطة النقل المرجعية، وسجلات «محلي فقط» السابقة تاريخية.

## ما نُفذ

- `db/raad/publication-gate.sql`: بوابة قاعدة بيانات على جميع مداخل النشر، لا مجرد تعطيل زر. الملف **خارج** `db/migrations` ولا ينفذه بدء التطبيق تلقائيًا.
- اعتماد مخزن بوقت خادم فعلي وبصمة النسخة الكاملة: النص والعنوان والمقتطف والصورة والتصنيف والكاتب ووسوم المادة. إنشاء اعتماد بعد محاولة النشر لا يصحح الترتيب الزمني بأثر رجعي.
- فصل مجموعتي صلاحيات `raad_gate_publisher` و`raad_gate_approver`، وكلتاهما NOLOGIN. الناشر لا يملك إنشاء أو تعديل قرارات الاعتماد، والمعتمد لا يملك تعديل المقالات أو نشرها. الأسماء أو JSON وحدها لا تمنح امتيازًا.
- رفض التعديل المباشر للنص المنشور؛ التحويل الصريح إلى مسودة، ثم التعديل وإعادة الاعتماد، مطلوب. انتهاء الاعتماد لا يسحب مقالًا منشورًا تلقائيًا.
- معرّف المقال ثابت على مستوى قاعدة البيانات؛ لا يمكن نقله إلى رابط آخر بكتابة SQL مباشرة، حتى إن لم تكن له وسوم أو مفاتيح خارجية مرتبطة.
- حماية تبديل الوسوم، واسم/رابط التصنيف، واسم/سيرة الكاتب المرتبطين بالنسخة. تعليق حساب الدخول وتغيير كلمة مروره لا يتوقفان بسبب اعتماد الأخبار؛ حالة الحساب الأمنية ليست نصًا تحريريًا محميًا بالبصمة.
- فحوص التبعيات تعود إلى حالة الانتظار بعد كل كتابة لاحقة، حتى عند تفريغ القيود المؤجلة بـ`SET CONSTRAINTS` ثم متابعة المعاملة؛ لا تصبح الكتابات التالية مستثناة من المراجعة.
- حجز معاملات كتابة المحتوى قبل أقفال الصفوف يمنع سباق نشر المادة وتغيير بياناتها المرتبطة. قراءات الزوار وتحديث عداد المشاهدات لا تأخذ الحجز العام ولا تغيّر تاريخ التحرير.
- التطبيق يفحص بايتات الصورة بمقابل SHA-256 المعتمد، بحد 5MiB ومهل نقل/قراءة محدودة. المفاتيح المحلية والسحابية تُكتب دون استبدال؛ المستورد صار ينشئ مسودات بمفاتيح صور عشوائية، داخل معاملة تمنع استيراد الرابط نفسه بالتزامن، ودون مشاهدات عشوائية.
- نطاق الموقع جزء من سجل الاعتماد؛ التطبيق يرفض النشر عند غياب SITE_URL أو عودته إلى localhost أو اختلافه عن النطاق المعتمد. السماح بـHTTP loopback في بيئة التطوير مقصور على اختبار محلي يحمل نطاق الاختبار نفسه، لا على الإنتاج.
- واجهة الإدارة تميز «نشر النسخة المعتمدة» عن إنشاء الاعتماد، وتعرض أخطاء مفهومة. حذف/إعادة إدخال مجموعة وسوم لم تتغير داخل معاملة لا يُعامل كخبر جديد.
- تركيب البوابة يرفض مجموعة صلاحيات موجودة تملك كائنات قاعدة بيانات، إضافة إلى رفض LOGIN/امتيازات الإدارة والعضويات؛ ملكية الجداول لا تُمنح للناشر أو المعتمد.
- خيارات اتصال موحدة في `lib/pg-connection-options.mjs` للويب وأدوات التشغيل واستيراد الاعتماد: TLS موثوق افتراضيًا، منع تعطيله خارج loopback، ومنع خيارات URL التي تستبدل إعدادات شهادة pg. تهيئة CA الإنتاجية واختبارها الفعلي ما زالا مطلوبين قبل النقل.

## حدود الثقة

المراجع والبصمات ليست توقيع هوية مشفرًا. `import-publication-approval.mjs` أداة **لمنسق موثوق** يقرأ سجل مهام متحققًا منه، وليست endpoint عامة. يلزم قرار نهائي صحيح، ونتائج المحقق والمحرر والمصور المطابقة، وبيان وسيط مؤكد، و`publicationSnapshot` فعلي مأخوذ من قاعدة البيانات ومربوط بمهمة المعتمد. لا يُقبل قرار قديم يفتقد هذه اللقطة.

صلاحية استدعاء إجراء تسجيل الاعتماد منفصلة في قاعدة البيانات. مالك قاعدة البيانات يستطيع تغيير المخطط أو تعطيل الحماية؛ لا تدّعي هذه البوابة عزله. يلزم استخدام حساب ويب غير مالك وغير superuser وغير عضو في مجموعة المعتمد، وعدم وضع بيانات اتصال المعتمد أو المالك في بيئة خدمة الويب. ضمان عدم استبدال الصورة خارج التطبيق يحتاج كذلك تقييد صلاحيات المخزن؛ مالك المخزن الإداري خارج حدود هذه الحماية.

## الأخبار الموجودة قبل التركيب

يُسجل baseline صريح للأخبار المنشورة الموجودة، **بدون** إنشاء APPROVED أو تغيير توقيتها أو متنها. هذا استثناء لاستمرار عرض النسخة المنشورة غير المتغيرة فقط. سحبها إلى مسودة يلغي الاستثناء؛ إعادة نشرها تحتاج اعتمادًا حقيقيًا. المادة 53 لا تُعد مثالًا على اعتماد سبق النشر، ولا يُعاد تأريخها عند تركيب البوابة.

## خطوات الإنتاج — تتطلب موافقة المالك

**الموافقة المحددة وصلت في 2026-10-27:** أجاب المالك «افعل الي تشوفه مناسب وصحيح» على سؤال صريح يشمل staging ثم الإنتاج، SQL وحسابَي الاتصال المحدودين والشهادة، وcommit/push وإعادة نشر Render. التنفيذ مشروط بنجاح staging والنسخة الاحتياطية والتحقق من الهدف؛ هذه الموافقة ليست سجل نجاح ترحيل أو تشغيل آلي. لا تُطلب الموافقة المحددة نفسها مجددًا.

قبل نافذة الإنتاج، طبّق الخطة على **staging منفصلة قائمة أو مأذون بإنشائها**: قاعدة وأدوار مستقلة، اتصال TLS فعلي، بناء وتشغيل بالإعداد الإنتاجي، واختبارات رفض/قبول وتعديل النسخة. لا يكفي نجاح Next.js dev المحلي أو الاختبارات الاصطناعية للسماح بالنقل. إن لم تتوفر staging مصرح بها يظل هذا شرطًا مفتوحًا.

1. مراجعة diff والنسخ الاحتياطي وتحديد نافذة قصيرة لإيقاف التعديلات التحريرية؛ تركيب SQL يأخذ أقفال كتابة مؤقتة على الجداول المعنية.
   بدأت المراجعة على `deploy/render-supabase` عند `59d5a49`، وأُنشئ لاحقًا فرع عمل `raad/publication-gate-staging`؛ `main` المحلي مختلف وقديم. أُعيد تأكيد أن Render الإنتاجي يتابع remote `main` عند `59d5a49`. الرفع الأول مخصص لفرع التجربة؛ الانتقال إلى main بعد نجاح staging والنسخة الاحتياطية، مع استبعاد الملفات غير التابعة للعمل.
2. بحساب ترحيل موثوق خارج خدمة الويب، تأكد من هوية قاعدة شُرفة ومن النسخة الاحتياطية، ثم نفّذ الملف **داخل معاملة واحدة**:
   `psql "$MIGRATION_DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f db/raad/publication-gate.sql`
   لا يوضع هذا الاتصال في Git أو المحادثة أو بيئة Next.js. الملف ينشئ مجموعتي الصلاحيات فقط، ولا ينشئ LOGIN أو كلمات مرور.
3. أنشئ بيانات اتصال مخصصة عبر إدارة أسرار مأمونة: حساب ويب عضو في الناشر فقط، وحساب منسق مستقل عضو في المعتمد فقط. تحقق من عدم امتلاكهما جداول/دوال أو صلاحيات إدارة أو عضويات إضافية. لا تنقل صلاحيات المالك إلى الناشر.
4. اختبر TLS وشهادة قاعدة البيانات للاتصالين وحساب الترحيل. الكود الجديد يتحقق من الشهادة افتراضيًا ويرفض تعطيل TLS بعيدًا؛ زوّد `DATABASE_CA_CERT` للويب وأدوات التشغيل و`RAAD_APPROVAL_DB_CA_CERT` للمنسق عند الحاجة، عبر إدارة الأسرار. لا يُفترض نجاح اتصال الإنتاج لمجرد نجاح فحوص إعدادات pg المحلية، ولا يُعطل التحقق لتجاوز خطأ شهادة.
5. نفّذ الترحيلات العامة المطلوبة بشكل صريح بحساب الترحيل. `npm start` أصبح `next start`؛ لم يعد بدء خدمة الويب يشغّل migrations بصلاحيات مالك.
6. بعد الموافقة على رفع التحديث وإعادة نشر الخدمة، بدّل `DATABASE_URL` إلى اتصال الناشر المحدود. لا تضع `RAAD_APPROVAL_DATABASE_URL` في خدمة الويب؛ يُزود به المنسق الموثوق فقط. لا تُرفع تغييرات `.vscode/` أو بيانات `.raad-local/` أو آثار المتصفح.
7. بعد نجاح staging السابقة، نفّذ smoke إنتاجيًا محدودًا لاستمرار عرض الأخبار القديمة والمشاهدات والحفظ كمسودة ورفض النشر غير المعتمد. إثبات قبول نشر جديد يستخدم مادة حقيقية مكتملة المراجعة ومصرحًا بنشرها؛ لا تستخدم خبرًا اصطناعيًا في النشر العام.

اكتملت خطوات النقل والتحقق في 2026-10-28، وأصبحت البوابة مفعلة على الموقع. العامل الدوري والسحب الآلي ما زالا مغلقين؛ مرجعهما منفصل عن تفعيل الحماية.

## تسجيل اعتماد جديد

يقرأ المنسق اللقطة عبر `SELECT raad_gate.article_snapshot($1)`، ويضع JSON كاملًا في `expectedTask.input.publicationSnapshot` **قبل** مراجعة حازم. القرار النهائي يجب أن يطابقها وتطابق البيانات الحالية عند التسجيل. كل نتيجة مساندة يجب أن تكون في السجل نفسه، مع ملف proof من مسار المراجعة الموثوق.

التنفيذ مقصود وصريح:

```text
node scripts/raad/import-publication-approval.mjs --journal <absolute-private-journal> --result-digest <sha256> --execute
```

يأتي اتصال المنسق من `RAAD_APPROVAL_DATABASE_URL`، دون تحميل `.env`، ولا يطبع البرنامج بيانات الاتصال. عدم وجود schema/صلاحيات أو انتهاء الاعتماد أو تغيّر النسخة يمنع النشر. الروابط الخارجية المتغيرة للصورة لا تُنشر مباشرة؛ يلزم أصل مرخص أو مملوك مستضاف بمفتاح ثابت وبصمة مؤكدة.

## الرجوع الآمن

عند فشل تركيب SQL داخل المعاملة، تُلغى العملية بكاملها. لا تُلغَ أقفال الاعتماد أو تُنشأ موافقات وهمية لتجاوز فشل نشر.

عند مشكلة في الكود الجديد: أبقِ بوابة DB وسجلها، وأوقف محاولات النشر الجديدة، ثم ارجع الكود بموافقة المالك. إذا استُعيد كود قديم يُشغّل migrations في `npm start`، استخدم أمر بدء مباشرًا `node node_modules/next/dist/bin/next start` مع حساب الويب المحدود؛ لا تعِد اتصال المالك إلى التطبيق. تبقى الأخبار المنشورة السابقة متاحة، وقد تُرفض محاولات التحرير/النشر القديمة برسالة خطأ بدل تجاوز البوابة. لا توجد آلية تلقائية لتعطيل البوابة أو إسقاط سجلها.

## التحقق المحلي الفعلي

- 17 مجموعة اختبار PostgreSQL على cluster TEMP مستقل وقاعدة `raad_gate_test`، مع معاملات واتصالين وصلاحيات فعلية؛ كلها نجحت. تشمل منع تغيير معرّف المقال، وإعادة تسليح الفحوص بعد `SET CONSTRAINTS`، ورفض مجموعة موجودة تملك الجدول.
- 4 اختبارات HTTP عبر نسخة Next.js معزولة ومتصفح headless جديد وحساب ناشر محدود: حفظ draft، منع النشر دون اعتماد، نشر اصطناعي بعد الاعتماد وفحص الصورة، ومنع تعديل النص المنشور مع بقاء النسخة القديمة؛ كلها نجحت.
- 24 اختبارًا لمستورد حزم الاعتماد وفحص بايتات الصور ونطاق النشر وخيارات TLS، ونجاح الحزمة الكاملة (**486**) وTypeScript. الجولتان 479/14 و462 أقدم من المراجعة الحالية؛ المرجع `PUBLICATION-GATE-VERIFICATION.md`.
- نجح بناء Next.js إنتاجي معزول بـ`--webpack` بعد استخدام إعداد Cairo المتغير، ثم نجح أمر `next build` الافتراضي بـTurbopack في نسخة اعتماديات فعلية. تشغيل بيئة الاستضافة الفعلية باقٍ ضمن staging، مع نجاح TLS وحسابي التجربة المحدودين؛ المرجع STAGING-VERIFICATION.
- لا PostgreSQL إنتاجي أو أسرار أو حسابات مستخدمين حقيقية نُقلت إلى بيئة HTTP؛ النسخة لم تحتوِ `.env`، واتصالها loopback، والبيئة الموروثة مقتصرة على متغيرات نظام لازمة.

هذه نتائج حماية محلية واستعداد ترحيل، وليست إعلان تشغيل دورة أخبار دائمة. تبقى حقوق الوصول إلى المصادر، وجرد المجدولات، والربط بالطابور والعامل، واختبار دورة خبر كاملة قبل الأتمتة أعمالًا مستقلة.
